# День 30. Локальная LLM как приватный сервис

Отдельный Python-сервис на основе дня 29: FastAPI, потоковый HTTP API, русский веб-чат, очередь и SQLite. Модель отвечает через установленный Ollama на вашем компьютере. Облачные LLM, внешние API генерации, CDN и загрузка моделей во время работы не используются.

## Быстрый запуск на этом компьютере

```powershell
cd D:\AIAdvent\advent-day-30-private-llm-service
powershell -NoProfile -ExecutionPolicy Bypass -File .\start-local.ps1
```

Откройте **http://127.0.0.1:8030**. Скопируйте значение `SERVICE_API_KEY` из локального `.env` и вручную вставьте в поле API-ключа. После подключения поле очищается, ключ остаётся только в памяти страницы. Перезагрузка страницы требует повторного ввода. Ключ не передаётся в URL, не попадает в localStorage/sessionStorage/cookie и не записывается в журнал.

При запуске дождитесь загрузки локальной embedding-модели: до её завершения HTTP-порт ещё не принимает подключения. При первом старте это может занять десятки секунд.

`-ExecutionPolicy Bypass` действует только для запущенного процесса PowerShell. Глобальная execution policy не меняется. Остановка приложения — **Ctrl+C** в его окне; отдельно запущенный Ollama остаётся работать.

## Установка и модель

Для новой установки нужен Python 3.11. `setup.ps1` создаёт собственную `.venv`, устанавливает зависимости из `requirements-lock.txt` и, если `.env` отсутствует, создаёт его со случайным ключом из 36 криптографически случайных байт. Существующий `.env` не перезаписывается. Для установки Python-пакетов нужен доступ к реестру пакетов; генерация и RAG после установки работают локально.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\setup.ps1
```

Используемая модель: **qwen3.5:4b, Q4_K_M**, runtime **Ollama**, endpoint **http://127.0.0.1:11434**. Исполняемый файл: `F:\LocalLLM\Ollama\ollama.exe`; существующие веса: `F:\LocalLLM\models`. Для запуска остановленного runtime в отдельном окне:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start-model.ps1
```

Скрипт использует установленный runtime, задаёт `OLLAMA_HOST=127.0.0.1:11434`, `OLLAMA_NO_CLOUD=1`, одну параллельную генерацию. Ничего не скачивает. Список уже установленных моделей можно посмотреть командой:

```powershell
& 'F:\LocalLLM\Ollama\ollama.exe' list
```

Чтобы выбрать другую **уже установленную локальную** модель, измените `LOCAL_LLM_MODEL` в `.env`, её окно контекста и путь к соответствующему токенизатору. Для семейства Qwen3.5 используется найденный локальный tokenizer JSON; для другого семейства текущий сервис применяет консервативную оценку по UTF-8 байтам. Неподходящий токенизатор Qwen к другой модели не применяется. Названия с `cloud` и модели с удалённым backend отклоняются. Генерация проверяет `/api/ps` после ответа: фактическое окно должно совпадать с `CONTEXT_WINDOW`.

Большие ресурсы подключены по настраиваемым путям:

| Ресурс | Настройка | Значение по умолчанию |
|---|---|---|
| Индекс E5, только чтение | `LOCAL_INDEX_PATH` | `D:\AIAdvent\advent-day-29-optimized-local-rag\output\structural.sqlite` |
| Qwen tokenizer | `LOCAL_TOKENIZER_PATH` | `D:\AIAdvent\advent-day-29-optimized-local-rag\models\tokenizer.json` |
| Embedding-модель | metadata индекса | `intfloat/multilingual-e5-small`, существующий локальный Hugging Face cache |
| Новая история | `DATABASE_PATH` | `data/sessions.sqlite` |
| Системные правила | `SYSTEM_PROMPT_PATH` | `prompts/system.txt` |

Исходные проекты не нужны в `PYTHONPATH`: подходящие модули поиска перенесены в `src/document_indexer`. Их индекс и tokenizer можно перенести вручную и поменять пути. Веса LLM не копируются. Если embedding-модель/индекс недоступны, обычный чат продолжает работать, RAG отключён в интерфейсе; явный запрос `use_rag=true` получает 503. Для полностью отключённого RAG задайте `RAG_ENABLED=false`.

## Ключи и история пользователей

`.env.example` содержит пустые значения секретов. `.env`, базы, логи и `.venv` исключены из Git. Не добавляйте их принудительно.

При ручной настройке скопируйте `.env.example` в `.env`. Новый ключ можно создать локально:

```powershell
.\.venv\Scripts\python.exe -B -c "import secrets; print(secrets.token_urlsafe(36))"
```

Поместите результат в `SERVICE_API_KEY`. Дополнительные независимые ключи задаются в `ADDITIONAL_API_KEYS` через запятую. Один ключ обозначает одного пользователя: все устройства с этим ключом видят его историю. Разные ключи имеют отдельные сессии и лимиты; обращение к чужой сессии возвращает 404. Смена ключа создаёт новую идентичность; прежняя история остаётся в базе и доступна со старым ключом, если он снова разрешён. Для отзыва ключа удалите его из конфигурации и перезапустите сервис.

История хранится локально, без шифрования на уровне приложения. Защита файлов следует правам вашей учётной записи Windows; при необходимости используйте шифрование диска. Только завершённая пара «вопрос–ответ» сохраняется одной транзакцией. Частичный ответ после ошибки не записывается. При сетевом разрыве после завершения проверьте историю перед повторной отправкой.

## Домашняя сеть и телефон

1. Остановите локальный сервис через Ctrl+C.
2. В `.env` задайте `HOST=0.0.0.0` для всех локальных интерфейсов или конкретный IPv4 вашего домашнего адаптера; `PORT=8030` можно изменить.
3. Выполните `powershell -NoProfile -ExecutionPolicy Bypass -File .\start-lan.ps1`.
4. Узнайте IPv4 компьютера:

```powershell
Get-NetIPConfiguration | Select-Object InterfaceAlias,IPv4Address,IPv4DefaultGateway
```

Используйте адрес активного Wi-Fi/Ethernet адаптера с домашним шлюзом. На телефоне в той же Wi-Fi сети откройте `http://<IPv4-компьютера>:8030`. `127.0.0.1` на телефоне указывает на телефон. Гостевая сеть или изоляция клиентов роутером может блокировать доступ.

`start-local.ps1` **всегда** привязывает приложение к `127.0.0.1`, даже если `.env` подготовлен для LAN. `start-lan.ps1` требует явно заданного сетевого HOST. Оба скрипта проверяют конфигурацию, доступность модели и отсутствие сетевого listener у Ollama. Пользователи обращаются только к порту приложения; порт 11434 остаётся локальным.

### Windows Firewall — только вручную

Для доверенной домашней сети разрешите входящий TCP-порт приложения только в профиле **Private**, только из `LocalSubnet`. Пример команды в PowerShell администратора (скорректируйте порт; скрипты проекта её не выполняют):

```powershell
New-NetFirewallRule -DisplayName 'Day30 Private LLM LAN' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8030 -Profile Private -RemoteAddress LocalSubnet
```

Удаление созданного правила:

```powershell
Remove-NetFirewallRule -DisplayName 'Day30 Private LLM LAN'
```

Не разрешайте сетевой доступ к Ollama, не отключайте Firewall, не настраивайте port forwarding/DMZ/UPnP для сервиса. Параметры ограничения правила описаны в [документации Microsoft](https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule).

Обычный HTTP разрешён только для доверенной домашней сети. Вне неё используйте VPN либо HTTPS. API-ключ сам по себе не шифрует соединение.

## API

Все `/api/*` endpoints требуют `Authorization: Bearer <ключ>`. Публичны только `/health` и статические файлы интерфейса, без истории или настроек секретов.

| Метод и путь | Назначение |
|---|---|
| `GET /health` | Жив ли процесс приложения |
| `GET /api/status` | Доступность модели/RAG, реальное окно модели, очередь и лимиты |
| `POST /api/chat` | Генерация; новая сессия при `session_id=null` |
| `GET /api/sessions` | До 100 последних сессий текущего ключа |
| `GET /api/sessions/{id}/messages` | Последние сообщения, `limit=100` (до 200), `before=<id>` для старых |

Пример тела запроса:

```json
{"session_id": null, "message": "Объясни WorkManager", "use_rag": true, "stream": false}
```

Ответ содержит `request_id`, `session_id`, `answer`, `sources`, `metrics`. У источника есть стабильный `chunk_id`, метка `[S1]`, текст фактически включённой цитаты, документ, URL при наличии и исходное положение. Это **источники, переданные модели**, а не автоматическое доказательство всех её утверждений. RAG использует локальный E5-поиск без дополнительного LLM rewrite. Длинный поисковый запрос сокращается отдельно до лимита E5, новое сообщение для генерации сохраняется целиком.

Фактические `prompt_eval_count`, `eval_count`, `total_duration`, `load_duration`, `prompt_eval_duration`, `eval_duration` передаются из финального кадра Ollama без выдуманных значений. Времена Ollama — **наносекунды**. Времена приложения `queue_ms`, `generation_ms`, `first_token_ms`, `total_ms` — **миллисекунды**. Протокол основан на [официальном API Ollama](https://docs.ollama.com/api/chat).

Для потокового ответа задайте `stream=true`. Content-Type: `application/x-ndjson`. Каждый кадр — отдельный JSON в отдельной строке:

```text
{"type":"queued","position":1,"request_id":"...","session_id":"..."}
{"type":"generating","request_id":"...","session_id":"..."}
{"type":"delta","text":"Часть ответа"}
{"type":"done","request_id":"...","session_id":"...","answer":"...","sources":[],"metrics":{}}
```

Без ожидания `queued` отсутствует. Пока нет текста, возможны кадры `heartbeat`. Ошибка до отправки заголовков возвращает обычный HTTP-код. Если поток уже открыт с HTTP 200, ошибка приходит финальным кадром `{"type":"error","status":504,"error":{"code":"generation_timeout","message":"..."},...}`. Клиент обязан дождаться `done` или обработать `error`, а не считать любой HTTP 200 успешной генерацией.

| HTTP | Код/причина |
|---|---|
| 400 | Неверный JSON/типы/пустое сообщение |
| 401 | Нет ключа или неверный ключ |
| 404 | Сессия отсутствует или принадлежит другому ключу |
| 409 | В этой сессии уже есть незавершённый запрос |
| 413 | Тело HTTP больше лимита, включая chunked transfer |
| 422 | Новое сообщение и системные правила не помещаются в контекст |
| 429 | Лимит генерации; заголовок `Retry-After` |
| 503 | Модель/RAG недоступны, очередь заполнена или истекло ожидание |
| 504 | Таймаут генерации |
| 502/500 | Неполный ответ runtime / внутренняя ошибка без stack trace |

При превышении очереди возвращается 503 с `Retry-After`. CORS по умолчанию не разрешает другой origin: чат и API обслуживаются одним приложением. Если нужен отдельный клиент, перечислите точные origin через запятую в `CORS_ORIGINS`; `*` запрещён. CORS не заменяет API-ключ.

## Ресурсы, контекст и ограничения

| Настройка | Начальное значение |
|---|---:|
| `RATE_LIMIT` / `RATE_WINDOW_SECONDS` | 10 / 60 |
| `GENERATION_CONCURRENCY` | 1 |
| `QUEUE_SIZE` | 5 ожидающих, дополнительно к активной генерации |
| `QUEUE_TIMEOUT_SECONDS` | 600, конечный предел для пяти ожидающих генераций |
| `GENERATION_TIMEOUT_SECONDS` | 120, абсолютный срок после начала обработки |
| `MAX_BODY_BYTES` | 65536 |
| `MAX_OUTPUT_TOKENS` | 512 |
| `CONTEXT_WINDOW` | 8192, рабочий профиль дня 29 |
| `RAG_TOP_K` / `RAG_MAX_TOKENS` | 3 / 2000 |
| `HISTORY_LIMIT` | 100 последних сообщений для подготовки prompt |

Все настройки читаются из `.env`; переменные окружения имеют приоритет. Sampling и CPU-настройки сохранены из профиля дня 29: temperature=0, top_p=0.95, top_k=20, presence_penalty=1.5, seed=28, num_gpu=0, num_thread=4, think=false. Размер ответа изменён с 768 на требуемые 512. Исходный профиль и prompt сохранены для прослеживаемости в `config/day29-optimized.json` и `prompts/day29-reference-v5.txt`; рабочие инструкции адаптированы к потоковому чату вместо структурированного JSON-ответа дня 29.

Бюджет включает системные инструкции, историю, RAG, новое сообщение и резерв ответа. Найденный Qwen tokenizer считает текст; шаблон сообщений оценивается консервативно: 256 служебных токенов плюс 24 на сообщение. Это не заявление о точном совпадении с внутренним chat template Ollama. Без tokenizer используется более строгая оценка по UTF-8 байтам. Метод и бюджет возвращаются в metrics. Сначала ограничивается RAG-бюджет, затем убираются старейшие полные пары истории, затем дополнительно сокращаются цитаты. Системные правила и новое сообщение не обрезаются. Реальный `prompt_eval_count` и окно из `/api/ps` дополнительно проверяются после генерации; [описание `/api/ps`](https://docs.ollama.com/api/ps).

Очередь FIFO существует в памяти одного процесса. Запускайте один worker: второй процесс с той же БД блокируется файловой блокировкой. Не запускайте одновременно бенчмарки дней 28–29 или другие клиенты на том же runtime, если нужен предсказуемый лимит нагрузки: очередь приложения не управляет чужими процессами. Повышение concurrency требует отдельного согласования с возможностями runtime и памятью; начальное значение остаётся 1.

Rate limit учитывает допущенные до проверки runtime попытки генерации, в том числе отклонённые из-за состояния очереди/runtime; окно скользящее. Перезапуск приложения сбрасывает лимиты и незавершённую очередь, но сохраняет завершённую историю. Сессии и сообщения не удаляются автоматически; размер БД растёт. Логи ротируются (2 МБ × 4 файла) и содержат только request_id, время, HTTP-статус, итоговый статус потока, длину очереди, код ошибки.

Интерфейс поддерживает безопасное подмножество Markdown: жирный текст, inline code и блоки кода. Сырые HTML, скрипты, изображения и произвольные ссылки модели не исполняются. Источники открываются только по `http/https` с `noopener noreferrer`; переход к оригиналу — отдельное действие пользователя.

## Проверки

```powershell
$env:PYTHONUTF8='1'
$env:PYTHONDONTWRITEBYTECODE='1'
.\.venv\Scripts\python.exe -B -m pytest -q
node --check web\app.js
node tests\test_web_safety.cjs
# Сначала запустите start-local.ps1 в другом окне:
.\.venv\Scripts\python.exe -B scripts\verify_live.py
# Отдельно, без других генераций:
.\.venv\Scripts\python.exe -B scripts\verify_recovery.py
```

`tests/` использует mock для предсказуемой проверки ограничений и отказов. `verify_live.py` отправляет настоящие HTTP-запросы в запущенный сервис и использует реальную Ollama. `verify_recovery.py` использует настоящую Ollama через обработчики приложения с отдельной тестовой БД, принудительным коротким таймаутом и реальным отказом TCP-соединения. Не запускайте оба сценария одновременно. Повторный live-прогон вскоре после предыдущего может упереться в rate limit: дождитесь нового минутного окна.

Итоги и измерения: [REPORT.md](REPORT.md), машинные данные — `reports/`. Тестовые запросы и ответы намеренно сохраняются в этих отчётах; это отдельные проверочные артефакты, не журнал пользовательских диалогов.

## Ручная проверка с телефона

1. Подключите телефон к той же домашней Wi-Fi сети. Запустите LAN-режим и настройте Firewall вручную.
2. Откройте адрес **компьютера** на телефоне. До ввода ключа история недоступна; неверный ключ отклоняется.
3. Введите верный ключ, отправьте «Ответь: телефон-30» и дождитесь потока ответа.
4. Откройте новый чат: предыдущая история не должна появиться в нём. Вернитесь в старый — история сохранена.
5. Включите «По документам», спросите про WorkManager, раскройте источник и цитату.
6. Перезагрузите страницу: ключ нужно ввести заново. После ввода прежние сессии снова доступны.
7. Проверьте узкий экран, клавиатуру, прокрутку, состояния ожидания. При временном отключении сети введённый текст должен остаться.
8. Для VPN-проверки отключите Wi-Fi на телефоне, включите мобильный интернет и VPN; используйте частный VPN-адрес компьютера. Без VPN этот адрес должен быть недоступен.

Запросы с самого компьютера к localhost или собственному LAN-IP не заменяют этот сценарий.

## Android по USB без изменения Windows Firewall

Для USB-подключения уже установлен ADB: `D:\AndroidSDK\platform-tools\adb.exe`.

1. Запустите сервис обычным `start-local.ps1` (либо используйте уже работающий экземпляр).
2. Подключите Android кабелем с передачей данных, включите «Отладку по USB» в настройках разработчика и подтвердите разрешение на телефоне.
3. При одном подключённом USB-телефоне выполните в обычном PowerShell:

```powershell
& 'D:\AndroidSDK\platform-tools\adb.exe' devices -l
& 'D:\AndroidSDK\platform-tools\adb.exe' -d reverse tcp:8030 tcp:8030
& 'D:\AndroidSDK\platform-tools\adb.exe' -d reverse --list
```

4. Откройте на телефоне `http://127.0.0.1:8030/`. Это адрес телефона, перенаправленный через USB на локальный сервис компьютера. Введите API-ключ вручную в поле страницы.
5. Оставьте USB подключённым. После переподключения телефона или перезапуска ADB проверьте `reverse --list` и при необходимости повторите `reverse tcp:8030 tcp:8030`.

Удаление только этого проброса:

```powershell
& 'D:\AndroidSDK\platform-tools\adb.exe' -d reverse --remove tcp:8030
```

Изменение Firewall, установка VPN и публикация в интернете не требуются. Если телефон имеет статус `unauthorized`, разблокируйте экран и подтвердите отладку; если список устройств пуст, проверьте кабель и настройки USB. Проверка USB не подтверждает доступ по Wi-Fi или VPN.
